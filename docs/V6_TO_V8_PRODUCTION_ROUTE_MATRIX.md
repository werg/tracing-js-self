# V6-to-V8 production routes and remaining replacement gates

This review is bound to producer `2cb668c233be139e37d3e5a78c8d4ab8a544cd62`
and native `6ef4794048a4d2ab0e732ccfd61c5cc3e7c3c822`. It supersedes the earlier
four-category route inventory for these exact sources. Later bootstrap,
terminal-history or training-validation changes need their own refreshed
source identity; historical results do not become final-pair qualification.

**No default or acceptance package is changed by this review.** V6 remains the
production semantic default. Explicit V8 routes, ordinary V8 training and
substantial recovery mechanisms exist, but complete behavioral parity,
installed legacy absence and release restoration remain separate gates.

## What is now enumerated

The [complete retained inventory](evidence/v8-production-routes-2026-11-22/README.md)
contains **205 canonical registrations**, assigned once each to **23 reviewed groups**:
36 package targets and conditions, 52 npm commands, five general CLI commands,
one Python console entry, 46 native command/group registrations, nine Python
module launchers, 34 canonical semantic JSONL operation names, 12 stream registrations
and ten raw stage definitions plus shared training defaults. The two semantic servers account for
12 legacy and 22 canonical V8 operations; eight additional accepted V8 separator
spellings are explicitly mapped to their canonical names. The independently
constructed real native parser agrees on every command and handler.

It also binds **191 producer and 155 native** candidate source/configuration/
workflow files, plus eleven explicit release/dependency/policy/container input receipts. These are file catalogs, not additional behavior or conformance
populations. The audit rejects added, removed or changed registrations and
source bytes, incomplete/duplicate review ownership and qualification claims.
It cannot prove every symbol behind an entry, every embedding caller, every
behavior combination or configuration held outside the repositories. Those
remaining inventories are explicit release obligations.

## Evidence boundaries and work order

Known join/progress recovery is integrated with complete acknowledged history;
creation/bootstrap and terminal close have additional candidate gates. Their
full application authority is stronger than a native mutation receipt and must
be qualified at every supported recovery boundary.

The old exact-pair full fits did complete 348 optimizer updates, 48 training
sources, 696 logical targets and 720 physical records. They did not independently
measure decoder positions/masks. Two newer, distinct expanded-contract fits are
running: `9cf091e6/1a69d9d` and `b4157952/2f3e6cf`; the latter additionally
records aggregate internal router rows/assignments. Their final results remain
unclaimed here. Each campaign has a separate two-update lifecycle and a fresh
348-update fit, not one continuous 350-update trajectory. Router aggregate
counts do not establish independent internal-router position coverage.

The immediate migration order is complete known-outcome application recovery;
final position-qualified training evidence; missing public selected/Natlang,
module and callback parity; a real V8 release package/restore route; then final
installed/default and operational qualification. Full language/edition and
learned-quality acceptance remain separately visible in the
[17-package ledger](LANGUAGE_COVERAGE_V8_CUTOVER_STATUS.md).
