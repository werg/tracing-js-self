# Selected orchestration execution lock prerequisite

`DurableSelectedOrchestrationExecutionLock` is a trusted-local Linux prerequisite for a future selected orchestration recovery protocol. It creates a stable lock inode under an owner-private directory and asks the system `flock` utility to acquire an exclusive nonblocking lock on an inherited descriptor. The utility must be an absolute executable owned by root or the current user and not group/world writable. The returned lease keeps that open-file description alive until `release()` closes its descriptor. The lock file is never removed or replaced. A process crash releases only that process's descriptor reference; a child that inherited the descriptor continues holding the same lock until it exits.

The capability is not wired into the orchestration driver or `restoreLatest`. Current checkpoints do not prove that their original driver held this lock, so this primitive does not authorize active restoration, pending-child replay, takeover, or retry. `inspectActiveRecovery` remains read-only evidence. No TTL, stale-PID check, manual lock-file deletion, or owner-name reuse may turn an old checkpoint into execution authority.

A future integration must make every original driver acquire the lock before native initialization and hold or inherit it across coordinator selections, child dispatch, and awaited service work. A recovered driver must acquire the same `(sessionId, streamId)` lock before rereading and validating the independently acknowledged history head. If the native worker can outlive its supervisor, the supervisor must pass the lease's borrowed `fileDescriptor` into that worker as an inherited descriptor so it keeps the lock while an RPC is in flight.

The lock only proves process exclusion. It cannot recover the outcome of a native request whose acknowledgement was lost. The current native selector keeps request IDs, pending counts, attempts, and acknowledgements in process memory; a fresh selector's `pending === 0` is not evidence about a previous process. Safe pending-child recovery still requires a native durable request identity, immutable outcome/acknowledgement readback, and stale-process fencing. Until that protocol exists, preserve pending native actions, lost acknowledgements, and unknown service outcomes as refusals.
